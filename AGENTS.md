# Enterprise Level Software Engineering AI Instruction

## 1 Overview

Use Qt 6 for application hosting and integration, with Qt WebEngine to render the frontend. Keep frontend code separate: HTML for structure, CSS for styling, and JavaScript for logic and interactions; never mix them in one file. Use C++ for the core backend, system operations, and performance-critical processing; use Python exclusively for AI intelligence. Keep all layers modular and communicate through well-defined interfaces, using Qt WebChannel for JavaScript-to-C++ communication when needed. Do not use QML, Qt Quick, or Qt Widgets to build the frontend.
## 2 First Priority
- **Roman Urdu:** Always communicate with the user in natural, simple Roman Urdu. Keep technical terms, code, commands, file names, and proper nouns unchanged. Never use Urdu or Hindi/Devanagari script unless requested.

## 3 Golden Rules
- **First-Time & As-Needed Project Analysis:** Analyze only the project areas required by the task. Reuse verified findings, inspect related dependencies and references when needed, and expand to broader or full-project analysis only when task scope, cross-component impact, uncertainty, or risk genuinely requires it. Do not repeat analysis without a concrete reason.
- **Cross-Platform Execution:** Follow existing platform-specific folders (e.g., Windows and macOS), implementing each requested platform according to its designated folder and structure.
- **Project Structure & Architecture:** Follow the existing project architecture and folder structure. Place files and any necessary subfolders only in their designated locations; do not introduce a new structure without a clear requirement.
- **Naming Standards:** Use clear, consistent, purpose-based names; every file and folder name must accurately reflect its actual responsibility, contents, and work.
- **Project Root Cleanliness:** Keep the entire project root clean. Do not create extra files or folders directly in the root. Keep all project work within the existing designated locations and create only root-level items explicitly required by the established project structure.
- **File Cleanliness:** Review project files when relevant to identify unused, obsolete, redundant, or unnecessary files. Verify references, dependencies, build configurations, and runtime use before classifying any file as unnecessary. Remove a file only when its lack of need is confirmed and deletion is safe. Never delete required, user-owned, or uncertain files.
- **Duplicate File Prevention:** Never create duplicate files anywhere in the project. Before creating a file, check whether the required file already exists; reuse or update the existing file when appropriate. Avoid copies with alternate names or unnecessary suffixes.
- **Meaningful Code Comments:** Add concise comments where they clarify non-obvious logic, decisions, or warnings; avoid comments that merely repeat the code.

## 4 Engineering Disciplines

- **Autonomous Domain Ownership & Professional Judgment:** Every engineer must understand and own their complete domain, including relevant knowledge, subdomains, responsibilities, tools, technologies, standards, and best practices. Discover unlisted needs, identify gaps and risks, improve and verify outcomes, and coordinate across disciplines. Titles and Core Responsibilities guide the work but do not limit it.
- **Autonomous Engineering Excellence:** Every engineer must proactively identify domain problems and improvement opportunities; research and compare suitable alternatives; independently choose, implement, optimize, and verify the best solution. Collaborate across disciplines, preserve project integrity, and escalate only decisions requiring user authorization or involving significant risk or irreversible impact.
- **Task-Scaled Execution & Scoped Analysis:** Match execution effort to task size and risk. Complete small, localized tasks directly by inspecting only the target component, its necessary references/dependencies, and relevant checks; do not trigger full-project analysis, broad engineer orchestration, or unnecessary workflows. Expand analysis, engineer involvement, and testing proportionately for complex, cross-component, architectural, security-sensitive, destructive, or high-risk tasks. Broaden scope only when evidence shows it is necessary.
- **Unified Testing, Development & Release Verification:** Launch and test the EXE in Debug mode. Relevant engineers verify their features and child features; QA Test and QA Automation Engineers independently plan and perform appropriate tests. Test deeply and iteratively—not superficially: investigate failures, fix root causes, and repeat relevant tests and regression checks until each feature works correctly and reliably; never stop after a basic or single successful test. Inspect source, compiler/linker, CMake, dependencies, runtime logs, terminal tabs, build output, Debug Console, and VS Code Problems; resolve project issues without suppressing diagnostics. Reload VS Code and recheck stale results. Never claim success while issues remain unresolved or unverified. After Debug tests pass and the Task Final Report is generated, launch and verify the Release EXE last.
- **File Ownership & Change Protection:** Check file ownership and references before modifying, replacing, renaming, or deleting files. Avoid unrelated changes and protect user data.
